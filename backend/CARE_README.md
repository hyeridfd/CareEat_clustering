# 돌봄 관리 기능 (유형 분류 · 돌봄 우선순위 · 솔루션 · 보호자 알림)

기존 설문 앱에 **요양원 담당자용 돌봄 관리**를 추가했습니다.

```
설문(기초·영양·만족도) ─▶ 척도 자동 채점 ─▶ 유형 배정(학습된 모델) ─▶ 돌봄 우선순위 점수
      ─▶ 솔루션 초안(규칙 근거 + LLM) ─▶ 가드레일 검증 ─▶ 담당자 수정·승인
      ─▶ 보호자 카카오 알림톡 + 리포트 링크 ─▶ 돌봄 수행·결과 기록 ─▶ 모델 재학습
```

구조는 **파이프라인 + LLM 1단계**입니다. 유형과 우선순위는 코드(모델·점수식)로 계산해 매번 같은 결과가 나오고, LLM은 솔루션 문장을 다듬는 데만 씁니다.

## 1. 설치 순서

### ① DB 테이블 추가
Supabase SQL Editor에서 `sql/care_schema.sql` 을 1회 실행합니다.
(추가 테이블: facility_staff, guardians, type_models, care_assessments, care_solutions, care_notifications, care_actions)

### ② 패키지 설치
```bash
cd backend
pip install -r requirements.txt          # 서버
pip install -r requirements-train.txt    # 모델 학습까지 할 PC
```

### ③ 유형 모델 등록
**A. 파일럿에서 만든 모델을 그대로 등록** (`bluefood_cluster.py fit` 결과 폴더의 model.joblib)
```bash
python -m care.train register --version v1-pilot-n55 \
  --model ../results/model.joblib \
  --names "양호 기능·양호 섭취형,섭취 저조·급식 불만족형,저작·연하곤란 고위험형" --activate
```
**B. Supabase에 쌓인 데이터로 새로 학습** (n=200 수집 후)
```bash
python -m care.train fit --version v2-n200 --k 3 --activate
```
- 재학습하면 새 군집을 이전 활성 모델의 유형 코드(C1/C2/C3)에 **자동 매칭**합니다(헝가리안 매칭, ARI 기록). 그래서 버전이 바뀌어도 유형의 의미가 유지됩니다.
- `models/<버전>/type_meta.json` 에서 유형명, 보호자용 표현(예: "집중 돌봄군"), 위험가중(risk_weight)을 검토·수정하세요.
- `models/` 폴더는 서버 배포에 포함되어야 합니다(Dockerfile은 `COPY . .` 로 포함).

### ④ 환경 변수 (`.env`)

식품·메뉴 그래프(Neo4j Aura)를 쓰려면 아래 네 개가 필요합니다. 비워 두면 스냅샷으로 동작합니다.
`NEO4J_URI` · `NEO4J_USER` · `NEO4J_PASSWORD` · `NEO4J_DATABASE`
(Render 환경변수에도 같은 값을 넣어야 배포본이 라이브로 붙습니다.)

```
LLM_PROVIDER=none            # openai | anthropic | none(규칙 기반)
OPENAI_API_KEY= / OPENAI_MODEL=gpt-4o-mini
ANTHROPIC_API_KEY= / ANTHROPIC_MODEL=claude-sonnet-4-5
KAKAO_MODE=dry_run           # 테스트 모드: 실제 발송 없이 미리보기·로그만
REPORT_BASE_URL=https://bluefood-survey.vercel.app   # 보호자 리포트 링크 주소
```
모델명은 각 사의 최신 이름으로 바꿔 쓰면 됩니다. 화면에서 요청마다 OpenAI/Claude/규칙을 골라 쓸 수도 있습니다.

### ⑤ 담당자 계정 발급
관리자로 로그인 → **담당자 계정** 탭에서 요양원·ID·비밀번호를 입력해 발급합니다.
담당자는 로그인 화면의 **요양원 담당자 로그인** → `/care` 로 들어갑니다(자기 요양원 어르신만 보입니다).

## 3. 핵심 로직

**유형 배정** (`care/engine.py`)
- 채점·섭취율·결측 대치는 파일럿 파이프라인(`care/bluefood_cluster.py`)과 동일합니다.
- 1순위와 2순위 유형까지의 거리 차가 작으면 **경계 사례**로 표시해 담당자가 확인하게 합니다.
- **유형 전이 판정**: 직전 평가와 유형이 달라졌을 때 직전 지표를 현재 모델로 다시 배정해 봅니다. 결과가 현재와 같으면 모델 교체 때문에 달라진 것(`model_change`, 알림 제외)이고, 다르면 실제 상태 변화(`state_change`, 우선순위 가산)입니다.
- 설문이 바뀐 어르신만 다시 평가합니다(‘전체 재평가’로 강제 가능).

**돌봄 우선순위** (`care/priority.py`, 0–100)
- 유형 위험가중 + 현재 상태(MNA-SF, BMI, 섭취율, 삼킴·씹기, 식사 도움, GDS, K-MBI) + 직전 대비 변화(체중 5%↓, MNA 2점↓, 섭취율 15%p↓, K-MBI 10%p↓) + 유형 전이 + 경계
- 45점 이상 **우선 관리**, 20–44 **주의 관찰**, 20 미만 **정기 관리**. 배점은 초기값이라 결과 데이터가 쌓이면 재보정하세요.

**솔루션** (`care/care_rules.py`, `care/solution.py`)
- 규칙 라이브러리(17개)가 지표에 맞는 **후보 조치**를 고릅니다. LLM은 이 후보 안에서만 개인화·정렬합니다.
- 가드레일: 후보에 없는 조치 제거, 약·용량·진단·처방 표현 차단, 보호자 문장의 전문용어·코드·길이 검사. 실패하면 규칙 원문으로 대체하고 화면에 표시합니다.
- LLM에는 이름·ID를 보내지 않습니다. LLM 호출이 실패하면 자동으로 규칙 기반으로 만듭니다.
- 담당자가 **승인한 솔루션만** 보호자에게 보낼 수 있고, 내용을 고치면 다시 승인해야 합니다.

**시설 단위 진단·개선안** (`care/facility.py`, `care/facility_rules.py`, `care/action.py`, `care/graph.py`)
- **Scan** — 개인 평가를 시설 단위로 집계합니다(위험군 비율·영양소 미달률·질환 분포·끼니/메뉴별 섭취율). 섭취 영양소가 저장돼 있지 않은 예전 평가는 식사 기록에서 즉석 계산해 채우고, 누가 왜 빠졌는지(`data_gaps`)를 함께 돌려줍니다.
- **Insight** — 19개 시설 규칙. `점수 = 규모(해당 어르신 %) × 심각도(3/2/1) ÷ 3`. 산식과 근거를 숨기지 않습니다. 영양소 기반 규칙은 분모가 5명 미만이면 판단하지 않습니다.
- **Action** — 우선순위마다 ① 공식 지침 근거(RAG, 문헌·쪽수) ② 식품·메뉴 DB 후보 ③ 잔반 최하위 메뉴의 같은 자리 대체안을 붙입니다.

**식품·메뉴 DB 연결** (`care/graph.py`, `care/graph_data/*.json`, `scripts/export_graph.py`)
- Neo4j 스키마는 **이름이 뒤집혀 있습니다**: `Food` = 요리(859), `Recipe` = 식재료(415), `Meal_Category` = 밥·국·주찬·부찬·김치·간식(6).
- **Neo4j Aura에서 직접 읽습니다.** 식품·메뉴 데이터가 주 단위로 갱신되기 때문입니다. 다만 개선안 하나에 집계 쿼리가 10번 넘게 돌고 Aura Free는 3일 미사용 시 일시정지되므로, **한 번 읽어 메모리에 얹어 두고 씁니다**(TTL 6시간, `GRAPH_TTL`로 조절).
  - Aura가 안 되면 `care/graph_data/*.json` 스냅샷으로 자동 폴백합니다 — 앱은 계속 돕니다. 화면 배지에 `실시간 연결` / `스냅샷`으로 표시됩니다.
  - 즉시 갱신: `GET /care/facility/graph-status?refresh=true`
  - 연결 진단: `python scripts/check_graph.py` — 설정·적재·표본 계산·안전장치를 한 번에 확인합니다.
  - 전체 DB(578,462 노드)에서 Care-Eat가 쓰는 범위는 0.3%(1,865 노드 / 15,311 관계)뿐이라 **Aura Free 한도(200k/400k)에 여유롭게 들어갑니다.** 원본에서 `Bioactivity`·`Compound`·`Species`·`Target`을 지우고 올린 서브그래프입니다.
  - 스냅샷 파일 갱신은 `python scripts/export_graph.py --cypher`.
- `Disease -RECOMMENDED_INGREDIENT-> Recipe` 관계는 **영양소를 매개로** 만들어져서, 예컨대 **'소금'이 고혈압 권장 재료로 들어와 있습니다**(마그네슘·칼슘을 함유하므로). 그래서 네 가지 안전장치를 강제합니다.
  1. **영양소가 1급 근거, 재료는 급원일 뿐** — `standard_key`가 `NUT:`이고 Nutrition 노드에 실제로 있는 영양소만 랭킹에 씁니다. 마그네슘은 Nutrition에 없어 검증 불가 → 소금이 걸러지는 지점이 바로 여기입니다. `GPT:`(LLM 추출 문구)·`CAT:`(식품군)은 참고용으로만 둡니다.
  2. **함량 기준 필터** — 100 kcal당 함량으로 줄 세우되 분모에 하한(30 kcal)을 둬 곤약·해조류가 밀도 랭킹을 독식하지 않게 합니다.
  3. **금기가 권장을 이긴다** — 금기 재료가 그 메뉴의 목표 영양소 급원 상위 3개에 들면 메뉴째 제외하고, 나머지는 `caution_ingredients`로 남겨 담당자가 판단합니다.
  4. **조미료 분류 제외** — 조미료류·조미식품·장류·당류·주류·유지류, 100 g당 나트륨 1,200 mg 이상, 그리고 이름이 조미·염장 재료인 것(멸치액젓·참치액·명란처럼 나트륨 값이 0으로 **비어 있는** 항목 포함)은 급원에서 뺍니다.
- **분량은 두 가지**입니다. `weight` = 제공 중량(발주·배식 기준), `nutri_weight` = 가식부 중량(영양 계산 기준). 7,532개 중 235개가 다릅니다 — 육수·건다시마는 0(우려내고 건져냄), 닭(뼈포함) 100 g → 65 g, 가자미 90 g → 65 g, 식용유 12 g → 4 g(흡유율). **영양은 반드시 `nutri_weight`로 계산합니다.** 이걸 안 하면 코다리조림 단백질이 51 g(틀림)으로 나옵니다. 제대로 하면 20.4 g입니다.
- 안전장치 ②는 이제 추정이 아니라 **1인분 실측**입니다. 목표 영양소 절대량으로 줄 세우되 **나트륨·포화지방 상한**(국 400 / 주찬 600 / 부찬 300 mg, KDRI 2025 노인 목표를 끼니로 나눈 값)을 함께 겁니다. 이걸 안 걸면 단백질 1등이 돼지갈비김치찜(단백질 40 g·나트륨 3,320 mg)이 됩니다. 후보가 너무 줄면 상한을 1.5배로 완화하고 `cap_relaxed`로 알립니다.
- **자료 한계(화면에도 표기)**
  - 국 198개 중 **125개는 육수가 재료로 등록돼 있지 않아** 중량이 건더기뿐입니다(`broth_missing`).
  - 멸치액젓·참치액·명란·건새우·건다시마는 **나트륨 값이 비어 있습니다.** 들깨무채국이 실제 900 mg대인데 5 mg으로 계산되는 식입니다. 저염 후보에서는 아예 제외합니다(`sodium_underestimated`) — 틀릴 거면 짜게 틀리는 편이 안전합니다.
  - 이름은 염장인데 재료에 그 염장품이 없는 경우가 있습니다(짜사이무침 → 재료가 생'무' 60 g, 나트륨 6 mg). 이름으로 걸러 냅니다.
  - 레시피 분량이 의심스러운 건(해물버섯누룽지탕: 건새우 40 g → 칼슘 1,629 mg)은 하루 기준치 초과로 **표시만** 하고 거르지 않습니다(`amount_outlier`).
- 연하장애는 그래프 관계가 1개뿐이라 **식형태 근거는 그래프가 아니라 공식 지침(RAG)에서만** 가져옵니다.

**보호자 알림** (`care/notify.py`)
- 알림톡은 사전 승인된 템플릿과 변수만 쓸 수 있어서 `CARE_REPORT_V1` 템플릿 + **리포트 링크 버튼** 구조로 만들었습니다.
- **건강정보 수신 동의**가 체크된 보호자에게만 보냅니다.
- 실제 발송 시: 카카오 비즈채널 개설 → 템플릿 심사(`notify.py` 의 문구와 동일하게) → 발송대행사(솔라피/NHN 등) 계약 → `SolapiSender` 또는 `NhnSender` 구현 → `KAKAO_MODE=live`.

## 4. 운영 전 확인할 것

- **개인정보**: 건강정보는 민감정보라 별도 동의가 필요합니다. 치매 어르신은 법정대리인 동의를 받고, 보호자에게 보내는 것(제3자 제공)과 모델 개선 목적 이용도 동의서·약관에 명시하세요.
- **Supabase 키**: 새 테이블에 보호자 연락처가 저장됩니다. 백엔드는 service key로, 프론트는 API만 쓰도록 하고 RLS를 켜 두는 것을 권장합니다.
- **의료기기 해당 여부**: 화면과 문구를 "돌봄·식사 관리 보조"로 유지하세요. 진단이나 위험 판정으로 표현하면 규제 검토가 필요할 수 있습니다.
